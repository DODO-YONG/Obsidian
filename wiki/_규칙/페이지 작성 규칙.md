# ✍️ 페이지 작성 규칙 (폴더 구조·산출물·네비게이션)

상위: [[00_홈]]

> `CLAUDE.md`에서 옮겨 온 상세 규칙. 위키 페이지를 새로 만들거나 구조를 바꿀 때만 읽는다.

## 3개 층

1. **`raw/`** — 원본 자료(pptx·pdf·docx·이미지 등). **읽기 전용. 절대 수정·삭제하지 않는다.** 진실의 원천.
   - 프로젝트별 원본은 `raw/projects/<프로젝트명>/`에.
   - 이미지·첨부는 `raw/assets/`(루트 공용). 임베드는 `![[파일명.png]]`로 — 옵시디언이 파일명으로 찾으므로 경로 무관.
2. **`wiki/`** — 내가 전적으로 소유하는 markdown 페이지. **다중 프로젝트 구조**:
   - `wiki/projects/<프로젝트명>/` — 프로젝트별 격리. 그 아래 `sources/`·`entities/`·`topics/`:
     - `sources/` — 각 원본 자료의 요약 페이지 (자료 1개 = 페이지 1개). 회의록은 `sources/회의/`.
     - `entities/` — 엔티티: 기업·기관·제품·사람 등
     - `topics/` — 개념·주제: 기술·결과물 등
     - `output/` — **내가 생성한 바이너리 산출물**(PPT·워드·엑셀·PDF 등, markdown 아님). 발표자료·보고서 파일을 여기에.
   - `wiki/shared/` — **여러 프로젝트에 걸치는** 엔티티(사람·공통 협력사·공통 기술). 예: `나.md`.
   - `wiki/_규칙/` — 위키 운영 상세 규칙(이 페이지, [[작업 규칙]]).
   - `wiki/00_홈.md`·`index.md`·`자료 현황.md` — 전체 길잡이(프로젝트 안 가림).
   - **승격 규칙**: 어떤 엔티티가 둘째 프로젝트에서도 등장하면, 그 프로젝트 폴더에서 `wiki/shared/`로 옮기고 링크는 그대로 둔다(파일명 기반이라 안 깨짐).
   - **새 프로젝트**: `wiki/projects/<이름>/{sources,entities,topics}/` 생성 + `index.md`에 `# 📁 프로젝트: <이름>` 섹션 + `00_홈`에 한 줄 추가. (`output/`는 첫 산출물 생길 때 만들면 됨)
3. **스키마** — `CLAUDE.md`와 `wiki/_규칙/`. 사용자와 함께 계속 다듬는다.

## 산출물 저장 규칙 (내가 만드는 파일이 어디로 가는가)
- **PPT·워드·엑셀·PDF 등 바이너리 산출물** → **항상** `wiki/projects/<프로젝트>/output/`. (루트·`raw/`에 던지지 않는다.)
- **markdown 산출물**(요약·분석·기획서 페이지)은 종전대로 `sources/`·`topics/` 등 성격에 맞는 곳.
- 산출물을 만들면 관련 source/topic 페이지에 `산출물:` 필드나 본문 링크로 경로를 남기고, `log.md`에 `output` 항목 기록.
- **파일명 규칙**: 바이너리 파일명 맨 앞에 날짜 — **`YYYY_MM_DD_제목.확장자`** (예: `2026_08_20_리빙랩_회의록.docx`). 내가 만드는 바이너리 산출물에 적용, 사용자도 raw 원본에 동일 형식 사용 권장. (위키 md 페이지명은 `제목_YYMMDD` — 링크 체계 보존.)

## 네비게이션 파일

- **`wiki/00_홈.md`** (사람용 시작 화면) — 진행 중인 프로젝트 목록 + 각 허브·공통 링크. 프로젝트가 늘면 한 줄 추가.
- **`index.md`** (내용 중심) — 위키 전체 카탈로그. **프로젝트별 섹션**(`# 📁 프로젝트: <이름>`)으로 정리, 페이지마다 링크 + 한 줄 요약. 매 ingest마다 해당 프로젝트 섹션 갱신.
- **`log.md`** (시간순) — append-only 기록. 각 줄은 `## [YYYY-MM-DD] ingest|query|lint|output | 제목` 형식으로 시작(grep 가능).

## 페이지 작성

- **frontmatter 필수**: `type`(source|entity|topic), `tags`, 그리고 적절히 `date`·`상태`·`출처수` 등. Dataview·그래프가 이걸 활용.
- **`project:` 필드 권장**: 프로젝트 소속 페이지는 frontmatter에 `project: <프로젝트명>` 기재(Dataview 필터용).
- **상호 링크는 `[[wikilink]]`로**. 엔티티·주제를 언급하면 링크.
- **계층은 한 칸씩만**: 각 페이지는 바로 위 한 칸(상위 MOC/허브)만 "상위로" 링크. 손주를 건너뛰어 직접 링크하지 않는다 → 그래프가 나무 모양을 유지.
- **기술/결과물 = 주제 페이지(topics), 기업 = 엔티티 페이지(entities)**. 둘은 N:N이므로 폴더가 아니라 링크로 연결. 기업이 참여하는 기술은 **각 페이지 본문에서만** 링크(요약표 헤더 등에 전체 나열로 링크 오염 금지).
- **모순 표기**: `> ⚠️ 모순: (기존) … ↔ (신규) … [출처]`.
- **분할 vs 통합**: 역할·예산 등 깊이 다룰 대상은 독립 페이지. 정보량 적고 가벼운 항목은 한 페이지에 `#` 섹션으로 묶고 `[[페이지#섹션|표시]]`로 링크 — 과분할 방지.
- **Dataview 사용 범위**: 상태 관리용 자동 집계(`자료 현황` 등)에만 Dataview 쿼리 사용. **`index`·허브 개요 같은 핵심 길잡이는 수동 텍스트 링크로 유지**(플러그인 없어도 보이도록).
- **코드 프로젝트 허브는 짧게**: 기능 설명은 `agents/<이름>/README.md`에 두고, 허브에는 설계 결정·확인한 것·남은 일만 적는다(중복 관리·중복 읽기 방지).

## 도메인 메모

프로젝트별 고정 사실(기관·기술·숫자)은 각 프로젝트 폴더의 `_<프로젝트명> 도메인 메모.md`에 둔다.
