# 📥 작업 규칙 (ingest·query·lint)

상위: [[00_홈]]

> `CLAUDE.md`에서 옮겨 온 상세 규칙. ingest·질문·점검을 할 때만 읽는다(매 대화 고정 토큰 절약).

## 1) Ingest (자료 수집)
사용자가 `raw/projects/<프로젝트>/`에 자료를 넣고 처리를 요청하면:
1. 자료를 읽는다. (어느 프로젝트 자료인지 먼저 확인)
2. **핵심 takeaway를 사용자와 먼저 확인한다** (혼자 단정하지 않는다).
3. `wiki/projects/<프로젝트>/sources/`에 요약 페이지 작성 (`원본:`에 정확한 raw 경로 기재).
4. 관련 엔티티/주제 페이지를 생성하거나 갱신 (자료 1개가 여러 페이지를 건드림). 여러 프로젝트 공통이면 `wiki/shared/`.
5. 새 정보가 기존 주장과 **모순되면 표시**한다(`> ⚠️ 모순:` 형식).
6. `index.md`의 해당 프로젝트 섹션 갱신, `log.md`에 한 줄 추가.

**원본 파일은 `raw/`에 그대로 둔다(옮기지·지우지 않는다).** ingest 완료 여부는 파일 위치가
아니라 기록으로 판단한다: `log.md`에 ingest 항목이 있고 + 해당 프로젝트 `sources/`에 요약 페이지가
있으면 "처리됨". 아직 source 페이지가 없는 `raw/` 파일이 "미처리".

### 1-b) 문서 상태(검토/확정) 추적
ingest 여부(시스템)와 **업무적 검토·확정 상태(사람)는 별개**다. source 페이지 frontmatter에:
- `ingest: 완료` (내가 처리했는가 — ingest 시 항상 완료)
- `검토상태: 초안 | 검토중 | 확정` (업무적으로 확정됐는가 — **사용자가 알려준 값만 반영**, 모르면 `미확인`)
- 같은 값을 태그로도: `#검토/초안` `#검토/검토중` `#검토/확정` `#검토/미확인`
검토상태는 내가 임의로 "확정"이라 단정하지 않는다. 사용자가 명시하지 않으면 `미확인`.
- **예외 — 기록성 자료는 자동 `확정`**: 회의록·녹취·수발신 메일처럼 "이미 일어난 일의 기록"은
  초안/확정 구분이 무의미하므로 묻지 않고 `확정`으로 기재한다. 검토상태를 물어볼 대상은
  **업무 문서**(계획서·설계서·발표자료·데이터셋 등 앞으로 바뀔 수 있는 산출물)만.
`wiki/자료 현황.md`(Dataview)에서 전체 자료의 상태를 표로 본다.

### 1-c) 자료가 많이 들어올 때
- 한 번에 파일이 많이(대략 10개 이상) 들어오면 **바로 ingest하지 않고 목록부터** 만든다: 파일명·종류·추정 날짜·한 줄 내용의 표를 보여주고 **어느 것부터 할지 사용자에게 우선순위를 묻는다.**
- 이유: 첫 ingest 결과(요약 깊이·페이지 나누는 방식)를 사용자가 확인한 뒤 규칙을 다듬고 확대하는 편이 안전하다.
- takeaway 확인 질문은 자료마다 따로 묻지 말고 **묶어서 한 번에** 묻는다.
- 같은 문서의 여러 버전이 보이면 최신본만 ingest하고 나머지는 source 페이지에 "구버전 N개 있음"으로만 적는다.

### 1-d) 파일 형식별 처리
- **hwp(한글)**: 직접 읽지 못한다. 발견하면 사용자에게 **한글에서 "PDF로 저장"** 후 다시 넣어 달라고 요청하고, 변환 전엔 ingest하지 않는다. hwpx는 시도해 본다.
- **엑셀·CSV**: 확장자가 아니라 **내용**으로 판단한다.
  - 일정표·품목 리스트·체크리스트·비교표처럼 **사람이 읽는 표(수십~수백 행)** → 일반 문서와 같이 ingest.
  - 판매 내역·로그·설문 원자료처럼 **수천 행 이상 쌓인 기록 데이터** → ingest(요약) 대상이 아니다. 아래 "데이터 파일 처리 절차"를 따른다.
  - 판단 기준: 행 수(수천 행 이상), 행의 모양(같은 형식의 기록이 반복되면 데이터 / 제목 행·병합 셀·메모가 섞이면 문서), 시트 구성(한 시트에 동일 구조가 쌓이면 데이터). **애매하면 사용자에게 묻는다.** 사용자가 "이건 문서로 다뤄줘"라고 하면 그대로 따른다.

### 1-e) 데이터 파일 처리 절차
1. **ingest 시**: 내용을 요약하지 않는다. source 페이지에 frontmatter `type: source`, `자료종류: 데이터`와 함께 **파일 설명·출처·시트/열 목록·행 수·기간**만 기록한다. (나중에 "그 파일에 ○○ 열 있었나?"에 파일을 다시 열지 않고 답하기 위함.)
2. **분석 요청 시** ("○○ 뽑아줘", "추이 보여줘"): 파이썬(pandas)으로 코드를 짜서 계산한다. 결과는 표·수치로 보여주고, 필요하면 차트를 `wiki/projects/<프로젝트>/output/`에 이미지로 저장한다.
3. **결과 저장**: 분석 결과와 계산 방법(어떤 열을 어떻게 집계했는지·필터 조건)을 `topics/`에 페이지로 남기고 원본 데이터 source 페이지를 링크한다. `log.md`에 `query` 항목 기록.
4. **반복 분석**: 같은 계산을 다시 할 가능성이 있으면 코드를 `tools/<이름>.py`로 저장하고 결과 페이지에 경로를 적는다. 다음엔 "지난달 것도 똑같이"로 재사용.
5. **전제**: 계산에는 PC에 파이썬이 필요하다. 없으면 사용자에게 알리고 설치를 도우며(회사 PC는 설치 권한 확인), 설치 전엔 1번(파일 설명)까지만 한다.
6. 원본 데이터는 절대 수정하지 않는다(raw 규칙). 정제본이 필요하면 `output/`에 새 파일로 만든다.
- **메일**: 본문을 txt로 저장한 것도 정상 자료로 취급한다(기록성 → 검토상태 `확정`).

## 2) Query (질문)
1. 어디를 볼지 알면 바로 그 페이지로 간다(`CLAUDE.md` 바로가기 표). 모를 때만 `index.md`를 먼저 읽는다.
2. 해당 페이지를 읽고 **인용과 함께** 답한다 (출처: `[[source 페이지]]`).
3. 가치 있는 답(비교표·분석·새로 발견한 연결)은 **위키에 새 페이지로 저장**해 축적한다.

## 3) Lint (점검)
주기적으로 위키 건강검진: 페이지 간 모순, 낡은 주장, 고아 페이지(들어오는 링크 0),
페이지가 없는 중요 개념, 빠진 상호참조, 웹 검색으로 메울 데이터 공백 — 찾아서 보고/제안한다.
